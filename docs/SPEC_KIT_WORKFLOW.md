# Lounge TV shared Spec Kit workflow

GPT Work remains the primary development environment. Codex manages Spec Kit, helps prepare
specifications and provides independent verification. GitHub stores the shared records.
This workflow does not create a replacement development branch or reconcile application branches.

## Start here in either environment

1. Read the [constitution](../.specify/memory/constitution.md).
2. Read [specification layout and status rules](../specs/README.md).
3. Read the selected feature's spec.md, plan.md, tasks.md and verification.md at one explicit ref.
4. Inspect current source and GitHub evidence. Do not infer current behavior from old chat history.
5. Confirm the scope and authorization recorded for that feature before implementation or builds.

Use the explicit branch in GitHub file links. The repository default branch may lag development.
When a feature ref changes, record both the previous and new source SHA and review the differences.

## Roles and handoff

| Record or action | Primary responsibility | Review |
|---|---|---|
| Product outcome, acceptance and authorization | Gary | GPT Work and Codex identify ambiguity |
| Specification and clarifications | Codex helps author; GPT Work checks source feasibility | Gary accepts scope |
| Implementation plan | GPT Work | Codex checks contracts, risks and constitution |
| Tasks and implementation | GPT Work | Codex verifies diff and evidence independently |
| Verification report | Codex | GPT Work responds; Gary accepts unresolved risks |
| Builds, pushes, merges and release | Only the actor explicitly authorized by Gary | Existing QA/release controls still apply |

A role assignment is not authorization to change application behavior or operate production.
Codex MUST NOT replace GPT Work's branch strategy. Existing branches and local work are preserved.

## Shared records

Use specs/<number>-<short-name>/ for spec.md, plan.md, tasks.md and verification.md. Related research,
contracts and checklists may live beside them. Each feature records owner, status, target branch,
source SHA, scope, approval evidence and open questions. Never store credentials or private URLs.
Use the [verification template](../specs/verification-template.md) for evidence.

- spec.md: user outcome, acceptance scenarios, constraints, non-goals and decisions.
- plan.md: affected components/contracts, implementation steps, QA isolation and recovery plan.
- tasks.md: stable task IDs, assignee, dependencies, completion checks and evidence references.
- verification.md: exact source and artifact identity, tests, device/visual checks, gaps and verdict.

Tasks are checked complete only with evidence. A code change, a passing test and a visual/device
approval are separate facts. An unavailable check is recorded as unverified.

## Lifecycle

1. Codex helps write a draft spec against current source. GPT Work reviews feasibility and Gary
   accepts scope. Resolve material ambiguities before planning.
2. GPT Work prepares the implementation plan; Codex reviews it against the constitution. Record
   acceptance and changes in the feature documents, rather than relying on conversation memory.
3. GPT Work maintains tasks and implements only authorized work using its existing branch process.
   Both tools read the same GitHub ref before writing. One writer owns each document at a time;
   re-read the latest revision before editing to avoid overwriting another tool's changes.
4. Codex independently compares implementation to the spec and records tests actually run, source
   SHA, limitations and evidence. GPT Work resolves findings and references the updated commit.
5. Gary decides whether to authorize builds, pushes, merge or release. Documentation does not
   grant those permissions. A green CI run alone is not production or physical-device approval.

## Tool compatibility

The installed Spec Kit 1.3.0 integration targets Codex, with nine skills in .agents/skills/ and
Bash helpers/templates in .specify/. GPT Work can read the same Markdown through its authorized
GitHub access and follow the acceptance criteria and tasks without executing a Codex skill.
Do not assume $speckit-* commands, automatic skill discovery, Bash execution or Spec Kit's workflow
engine are available in GPT Work. The bundled workflow is not a GitHub Actions workflow and must
not be auto-executed as part of installation.

Codex may use $speckit-specify, $speckit-clarify, $speckit-plan, $speckit-tasks and $speckit-analyze
within approved scope. These commands are optional authoring adapters to the shared files.
$speckit-implement and automated implementation workflows are not authorized
by this adoption. GPT Work continues to implement through its existing process.

Feature directory selection is local state. Codex can set SPECIFY_FEATURE_DIRECTORY to
specs/<number>-<short-name> (and optionally SPECIFY_FEATURE to the feature identifier), or use the
checkout-local .specify/feature.json generated by the tooling. The identifier alone does not resolve
the directory. Do not commit that pointer, extension local overrides, adapter packages or linked
Supabase metadata.

## GitHub read-back acceptance

Before publication, local validation can prove Markdown portability and working links, but cannot
prove that GPT Work has read files that have not yet been pushed.
After an explicitly approved push, give GPT Work a link to this file on the integration branch.
Ask it to read the linked constitution, specs README and verification template, then report:

- the branch and immutable commit it read;
- the ten constitution principles and restrictions on production operations;
- where the feature specification, plan, tasks and verification belong;
- one acceptance criterion and its corresponding task/evidence, when a feature exists;
- its understanding that it remains the primary implementer and must not auto-run Codex commands.

Record the response and source ref as acceptance evidence. A Codex GitHub read-back of the same
files checks publication and access; it does not substitute for GPT Work's own confirmation.
